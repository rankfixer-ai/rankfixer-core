How to Build a RAG Pipeline (And What It Actually Takes)

How to Build a RAG Pipeline (And What It Actually Takes)

The Hook

A working RAG demo takes an afternoon. A production RAG system takes weeks — and most of that time isn't spent on the parts the tutorials cover.

The tutorials show you how to chunk, embed, retrieve, and generate. They don't show you what happens when a document updates, when retrieval returns the wrong chunk, when the model ignores the context it was given, or when a user asks a question your corpus can't answer.

This is the 7-step pipeline from What is RAG? — but this time, with the parts that actually take the time.

The Five Things That Break in Production

This is the section tutorials skip. Each one is a real failure mode I've seen in deployed systems.

Break 1: Retrieval Returns the Wrong Chunks

The symptom: The answer is confidently wrong even though the correct document exists in your corpus.

Why it happens: Semantic search alone isn't enough. The query "return window" doesn't match a chunk that says "items may be sent back within 14 days" — same meaning, different words. Or worse, it matches a chunk about a different product's return policy.

This is one of the most common sources of errors in production RAG. The chunk exists. The embedding model doesn't think it's relevant.

What it takes to fix: Three layers of retrieval:

  1. Dense retrieval (embeddings) — catches semantic matches
  2. Sparse retrieval (BM25, keyword) — catches exact matches the embedding model missed
  3. Re-ranking (cross-encoder) — re-scores the top-K results for precision

This is hybrid search + re-ranking. It's where much of the engineering time goes. Hybrid retrieval with re-ranking can substantially improve recall over dense-only retrieval. The exact numbers depend on your corpus, queries, and embedding model — they need to be measured on your own data.

Break 2: The Model Ignores the Retrieved Context

The symptom: You retrieved the right chunk. The model still hallucinated. Or it answered from its training data instead of the context you provided.

Why it happens: Prompt design. If the context is too long, the model gets lazy and falls back on what it already knows. If the instructions are weak ("use the context if relevant"), the model interprets "if relevant" liberally. If there are conflicting instructions elsewhere in the prompt, the model picks the one that feels more natural.

What it takes to fix: Three prompt-level patterns that work:

  1. Explicit grounding: "You MUST answer ONLY from the context below. Do not use outside knowledge."
  2. Citation requirement: "Cite the specific section your answer comes from."
  3. Structured output: Force JSON with answer and citation fields.

Even with these, models can ignore grounding instructions — especially when the context is long, conflicting, or noisy. This is one of the reasons evaluation is necessary: you can't assume grounding works without measuring it.

Break 3: Documents Change and the System Rots

The symptom: The system worked at launch. Three months later, answers are stale. The AI references a policy that was updated two months ago. It gives last quarter's pricing.

Why it happens: The document store isn't synced with the source. There's no re-indexing pipeline. Documents were ingested once and never updated.

What it takes to fix: An ingestion pipeline that handles:

  1. Change detection: When was this document last modified?
  2. Incremental re-embedding: Re-embed changed chunks, not the whole corpus
  3. Versioning: When a document changes, the old chunks are replaced, not duplicated

This is infrastructure, not a feature. It requires a cron job or webhook that watches your document source and triggers re-ingestion. Most tutorials don't cover this. Most production systems need it.

Break 4: The Corpus Doesn't Have the Answer

The symptom: A user asks something your documents don't cover. The model doesn't say "I don't know." It makes something up.

Why it happens: The model is trained to favor answering. There's no fallback behavior. When retrieval returns low-confidence chunks, the model uses them anyway rather than admitting the corpus is incomplete.

What it takes to fix: Graceful failure design:

  1. Retrieval score threshold: If the top result's similarity score is below a threshold calibrated to your evaluation set, don't generate — say "I don't know"
  2. Confidence-based routing: Low confidence → "I don't know" or human handoff
  3. Fallback responses: Pre-written responses for common out-of-scope queries

This is where RAG crosses into product design. You're not just building a retrieval system. You're designing what happens when retrieval fails.

Break 5: You Can't Tell If It's Working

The symptom: No idea whether answers are accurate. No metrics. No alerts. You find out the system is broken when a customer complains.

Why it happens: No evaluation framework. Most tutorials stop at "it works on my test query." That's not a production system.

What it takes to fix: An evaluation pipeline with three layers:

Metric What It Measures Tool
Recall@K Did retrieval find the right chunk? Ragas, custom
Groundedness Is the answer derived from retrieved text? Ragas, TruLens
Hallucination rate What % of answers contain fabrication? LLM-as-judge

Run this evaluation on every query in development. Sample it in production. Alert when metrics drop below threshold.

This is the "budget roughly 20-30% of build cost for evaluation" point from Piece #1. It's not optional. It's what separates a demo from a product.

What a Real Build Timeline Looks Like

Here's what building a production RAG system actually takes:

Phase Duration What Happens
Discovery 1 week Document audit, query analysis, success criteria
Prototype 1-2 weeks The demo — works on clean data, happy path
Retrieval tuning 2-3 weeks Hybrid search, re-ranking, query rewriting
Generation tuning 1-2 weeks Prompt design, citation, fallback
Evaluation 1-2 weeks Metrics, test set, regression checks
Deployment 1 week Integration, monitoring, handoff

Total: 6-10 weeks for a production system.

Compare to "a weekend for a demo." The gap is the five things above.

Build vs. Hire: An Honest Assessment

The question isn't whether you can build it. It's whether building it is the best use of your team's time.

You should build in-house if... You should hire if...
You have ML engineers with spare cycles Your team is already at capacity
RAG is core to your product roadmap RAG is a feature, not the product
You have months to iterate You need it working in weeks
You'll maintain it long-term You want it handed over and maintained by you

The honest frame: "Hire if the opportunity cost makes sense." Not "hire because it's hard." Hire because your team's time is worth more spent elsewhere.
