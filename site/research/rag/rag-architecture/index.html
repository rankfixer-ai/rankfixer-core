RAG Architecture Explained: Chunking, Embeddings, Retrieval, and the Decisions That Matter

RAG Architecture Explained: Chunking, Embeddings, Retrieval, and the Decisions That Matter

The Hook

Two RAG systems can use the same model, the same vector database, and the same documents — and perform completely differently. The difference is architecture: how you chunk, which embedding model you choose, whether you use hybrid search, whether you re-rank, and how you evaluate.

This is a technical reference for each decision — what to choose, why, and what breaks when you get it wrong. It assumes you've read What is RAG? and How to Build a RAG Pipeline. It goes deeper than both.

Decision 1: Chunking Strategy

This is the highest-leverage decision and the most misunderstood.

The strategies

Strategy How It Works Best For Breaks When
Fixed-size Split every N tokens with overlap Homogeneous text Documents have structure (headers, tables, code)
Recursive Split by hierarchy (headers → paragraphs → sentences) Structured docs (manuals, policies, wikis) Text is unstructured prose
Semantic Split at meaning boundaries (embedding similarity drops) Mixed content, high variance Latency and cost matter (requires embedding during chunking)
Document-aware Preserve tables, code blocks, lists as single chunks Technical docs, code, financial reports Documents are prose-heavy

The parameters

  • Chunk size: 200–500 tokens is the default. Smaller chunks = more precise retrieval but less context. Larger chunks = more context but retrieval noise.
  • Overlap: typically 10–20% of chunk size. Preserves boundary context. Too much = duplication and cost.
  • Metadata: Every chunk should carry source document, section heading, version, and position. Without metadata, you can't trace answers back to sources.

What breaks

Wrong chunk size means retrieval returns fragments that don't contain the answer. A 100-token chunk might split a policy in half: "Returns are accepted within..." and "...14 days of purchase." The retrieval system finds the first half, misses the second, and the model answers "Returns are accepted within..." — incomplete and misleading.

This is one of the most common sources of production failures.

The pattern

# Recursive chunking with metadata preservation
            def chunk_document(doc, chunk_size=300, overlap=50):
                chunks = []
                sections = split_by_headers(doc)  # Respect document structure
            
                for section in sections:
                    paragraphs = split_into_paragraphs(section)
                    for i in range(0, len(paragraphs), chunk_size - overlap):
                        chunk_text = " ".join(paragraphs[i:i + chunk_size])
                        chunks.append({
                            "text": chunk_text,
                            "source": doc.filename,
                            "section": section.heading,
                            "version": doc.version,
                            "position": i
                        })
                return chunks

Decision 2: Embedding Model

The embedding model determines what "similar" means. Change it, and every vector in your store is invalid.

The landscape

Model Dimensions Cost Best For
OpenAI text-embedding-3-large 3072 $0.13/1M tokens General-purpose, highest quality
OpenAI text-embedding-3-small 1536 $0.02/1M tokens Cost-sensitive, high volume
Cohere Embed v3 1024 $0.10/1M tokens Retrieval-optimized
BGE-large (BAAI) 1024 Self-hosted Privacy, no API costs
E5-large (Microsoft) 1024 Self-hosted Multilingual
Nomic Embed v2 768 Self-hosted Long context, efficient

The commitment

Pick one and commit. If you ingest 100K chunks with OpenAI text-embedding-3-small and later switch to BGE-large, you must re-embed everything. There's no translation between embedding spaces.

What breaks

Mixing embedding models across ingestion and query. If you embed documents with model A and queries with model B, the similarity scores are meaningless. This is a subtle bug — the system runs, but retrieval is silently degraded.

The pattern

# Consistent embedding across ingestion and query
            from openai import OpenAI
            
            client = OpenAI()
            
            def embed_text(text, model="text-embedding-3-small"):
                response = client.embeddings.create(
                    input=text,
                    model=model
                )
                return response.data[0].embedding
            
            # Ingest: embed chunks
            chunk_vectors = [embed_text(chunk["text"]) for chunk in chunks]
            
            # Query: embed question with the SAME model
            query_vector = embed_text(user_question)

Decision 3: Retrieval Pattern

This is where the real engineering is. Dense retrieval alone is the starting point, not the production default.

The patterns

Pattern How It Works When to Use
Dense (semantic) Vector similarity search Default starting point
Sparse (keyword) BM25, TF-IDF on exact terms Codes, names, error messages, exact-match queries
Hybrid Combine dense + sparse scores Production default — catches both semantic and exact matches
Re-ranked Retrieve N candidates, rerank to top K When precision matters (regulated, high-stakes)
Multi-query Generate query variants, retrieve all, deduplicate When user queries are vague or ambiguous
Parent-child Index small chunks, return larger context window When the answer spans multiple chunks

Why hybrid is the default

Dense retrieval fails on exact-match queries. A user searching for "error code 0x80070005" needs keyword matching — the embedding model doesn't know that specific hex code. Sparse retrieval fails on semantic queries. A user asking "why won't my app install?" needs semantic matching — no keyword overlap with "error code 0x80070005 access denied."

Hybrid catches both.

What breaks

Retrieval returns top-k chunks by similarity — but similarity isn't relevance. A chunk about "return policy for electronics" might be semantically similar to a query about "return policy for clothing" but factually wrong. Re-ranking fixes this by scoring candidates against the query with a cross-encoder.

The pattern

# Hybrid retrieval with re-ranking
            def hybrid_retrieve(query, vector_store, bm25_index, k=5, n=20):
                # Step 1: Dense retrieval (semantic)
                dense_results = vector_store.similarity_search(query, k=n)
            
                # Step 2: Sparse retrieval (keyword)
                sparse_results = bm25_index.search(query, k=n)
            
                # Step 3: Combine and deduplicate
                combined = merge_results(dense_results, sparse_results, 
                                         dense_weight=0.7, sparse_weight=0.3)
            
                # Step 4: Re-rank top candidates
                reranked = reranker.rerank(query, combined, top_k=k)
            
                return reranked

Decision 4: Generation and Grounding

The model's job is to summarize retrieved chunks, not to reason about the world. The prompt has to make that explicit.

The grounding patterns

  1. Explicit instruction: "You MUST answer ONLY from the context below. Do not use outside knowledge."
  2. Citation requirement: "Cite the specific section your answer comes from."
  3. Structured output: Force JSON with answer, sources, and confidence fields.
  4. Fallback instruction: "If the answer isn't in the context, say 'I don't know.'"

What breaks

The model ignores the context and answers from training data. This happens when: - The context is too long (model gets lazy) - The instructions are weak ("use the context if relevant") - There are conflicting instructions elsewhere in the prompt - The model is under pressure to always produce an answer

Even with strong grounding, models can ignore instructions — especially when the context is long, conflicting, or noisy. That's why you need evaluation.

The pattern

# Grounded generation prompt
            GROUNDED_PROMPT = """
            You are a factual assistant. Answer the question using ONLY the context provided.
            
            RULES:
            1. Answer ONLY from the context. Do not use outside knowledge.
            2. Cite the specific section your answer comes from.
            3. If the answer is not in the context, say "I don't know."
            4. Do not guess, infer, or fill in gaps.
            
            Context:
            {context}
            
            Question:
            {question}
            
            Respond in JSON:
            {{
              "answer": "your answer here",
              "sources": ["section 1", "section 2"],
              "confidence": "high" | "medium" | "low"
            }}
            """

Decision 5: Evaluation

This is the section that differentiates the piece. Most architecture articles skip evaluation. Production systems can't.

The metrics

Metric What It Measures How to Compute Target
Recall@k Did retrieval find the right chunks? Labeled test set >85%
MRR How high did the right chunk rank? Labeled test set >0.8
Groundedness Is the answer from the context? LLM-as-judge >90%
Faithfulness Does the answer contradict the context? LLM-as-judge >95%
Answer relevance Does it answer the question? LLM-as-judge >85%
Latency How long does it take? Instrumentation <3s
Cost per query What does it cost? Token counting Varies

The evaluation pipeline

  1. Build a test set: 100–500 question-answer pairs with labeled relevant chunks
  2. Run evaluation: Every query in development, sampled in production
  3. Alert: When metrics drop below threshold, trigger investigation
  4. Iterate: Fix the architecture decision that's causing the degradation

What breaks

No evaluation means you don't know if a change made it better or worse. You deploy a new embedding model, retrieval gets worse, and you don't find out until customers complain. Evaluation is continuous infrastructure, not a phase.

The pattern

# Evaluation pipeline
            def evaluate_rag_system(test_set, rag_pipeline):
                results = []
            
                for question, expected_answer, relevant_chunks in test_set:
                    # Run the pipeline
                    answer = rag_pipeline.query(question)
            
                    # Measure retrieval
                    recall_at_5 = compute_recall(answer.retrieved_chunks, relevant_chunks, k=5)
                    mrr = compute_mrr(answer.retrieved_chunks, relevant_chunks)
            
                    # Measure generation
                    groundedness = judge_groundedness(answer.text, answer.retrieved_chunks)
                    faithfulness = judge_faithfulness(answer.text, answer.retrieved_chunks)
                    relevance = judge_relevance(answer.text, question)
            
                    results.append({
                        "question": question,
                        "recall@5": recall_at_5,
                        "mrr": mrr,
                        "groundedness": groundedness,
                        "faithfulness": faithfulness,
                        "relevance": relevance
                    })
            
                return aggregate_metrics(results)

The Architecture Decision Matrix

Decision Default When to Change
Chunking Recursive, 300–500 tokens, 15% overlap Structured docs → document-aware; mixed content → semantic
Embedding OpenAI text-embedding-3-small Privacy requirements → self-hosted; multilingual → E5
Retrieval Hybrid (dense + sparse) + re-ranking Low latency requirement → dense only; high precision → add multi-query
Generation Grounded prompt + structured output + citations Regulated industry → add calibrated confidence thresholds and human handoff for low-confidence responses
Evaluation Recall@k + groundedness + faithfulness Production → add latency and cost monitoring; regulated → add full audit trail
