Case Study: Building an Adaptive Learning Engine

Case Study: Building an Adaptive Learning Engine (Where RAG Fits)

The Hook

The AI Learning Engine is a competency-based learning platform. Learners progress by demonstrating skills — not by completing lessons. The system tracks evidence, verifies competencies, and gates progression.

It's not a RAG system. But it taught me the architectural decisions that a RAG system would need to make — the ones covered in RAG Architecture Explained.

This case study covers what the learning engine is, where RAG fits into it, and what building the application layer taught me about the retrieval layer beneath it.

The Brief

The project started with a constraint: a learning system where competency demonstration is the only authority for progression. Not quiz scores. Not time spent. Verified evidence.

The domain

Aspect Description
Users Learners moving through a 4-level competency hierarchy (AI Literacy → Application → Engineering → Research)
Structure 4 competency dimensions (Cognition, Skills, Thinking, Values), each with declarative competencies
Evidence Append-only record of learner actions — not scores, but what the learner actually did
Verification Rules that map evidence to competency verification
Progression Competency gates — you can't advance until verified

The constraint

PRL (Procedural Representation Language) is the canonical representation layer. Every competency, lesson, assessment, evidence record, and verification rule is a PRL program. The compiler validates structure. The engine executes logic. The evidence store is append-only.

This means: the learning logic is decoupled from the content. New lessons can be added as PRL files without modifying engine code.

The Architecture

Curriculum Intent (curriculum/*.prl)
                    ↓
            PRL Compiler (prl/learning/ — extends prlc/pipeline.py)
                    ↓
            Learning Runtime (engine/)
                    ↓
            Learner Interaction (app/interactive_lesson/)
                    ↓
            Evidence → Verification → Competency → Progression

The system is a pipeline of PRL programs. The compiler validates. The runtime executes. The evidence store records. The competency tracker gates.

This is the application layer — the logic that decides what a learner does next based on evidence.

But here's the gap: what if a learner asks a question that isn't covered by the lesson flow? "Why does face recognition fail in low light?" The lesson demonstrates it, but the explanation lives in the curriculum content. To answer dynamically, you need retrieval.

That's where RAG fits.

Where RAG Fits

The learning engine doesn't have a RAG pipeline today. But here's where one would plug in:

The retrieval need

Learners ask questions during lessons. Some are answered by the lesson flow. Others require pulling from:

  • Lesson content (PRL source files)
  • Assessment rubrics
  • Evidence records (past learner actions)
  • External documentation (when the curriculum references external standards)

A RAG pipeline would:

  1. Ingest — lesson PRL files, assessment rubrics, evidence records
  2. Chunk — by PRL primitive type (competency, lesson, assessment, evidence)
  3. Embed — with a model that understands structured PRL syntax
  4. Store — in a vector DB indexed by competency and dimension
  5. Retrieve — hybrid search (semantic + exact-match for PRL keywords like competency_id)
  6. Generate — grounded answers that cite the specific PRL section

This is the architecture from Piece #6 applied to a specific domain.

What Broke (And What It Taught Me)

Building the learning engine surface three failures that map directly to RAG architectural decisions.

Failure 1: Chunking by Token Count Broke PRL Structure

What I did first: Treat PRL files like any other document. Split by token count — 500 tokens, 50 overlap.

What broke: PRL primitives span multiple lines. A competency definition is 5-15 lines. Chunking by token count split primitives mid-definition. The compiler couldn't parse fragments. The system silently dropped malformed chunks.

The fix: Chunk by PRL primitive boundary, not token count. Each chunk is one complete primitive (one competency, one assessment, one evidence record). Token count varies — 50 to 300 tokens per chunk.

The RAG lesson: This is Piece #6's chunking decision in practice. The default (fixed-size chunking) is wrong for structured content. You chunk by the structure of your documents, not by a number.

Failure 2: The Evidence Store Was Append-Only But Not Queryable

What I built: An append-only evidence store. Every learner action is recorded. The store is immutable — evidence is never deleted or modified.

What broke: The system couldn't answer "what evidence has this learner submitted for competency X?" The store had no query layer. It was a write-optimized log, not a read-optimized index.

The fix: Add a separate query layer — an index that maps (learner_id, competency_id) to evidence record IDs. The store stays append-only. The index is derived.

The RAG lesson: This is Piece #6's retrieval pattern. Your vector DB is the query layer. Your source documents are the append-only store. You need both — and they serve different purposes.

Failure 3: Verification Rules Couldn't Explain Themselves

What I built: Verification rules map evidence to competency verification. A rule says "if evidence type is experiment_result AND score > 0.8, verify competency."

What broke: When the system says "competency verified," there's no explanation of why. The learner sees a green checkmark. They don't see which evidence triggered the rule. They can't contest it.

The fix: Add a verification explanation layer. When a rule fires, the system generates a human-readable explanation: "Competency verified based on evidence [record-42] — experiment_result with score 0.85, meeting threshold of 0.8."

The RAG lesson: This is Piece #4's Sign 4 — the AI answers but can't cite sources. Grounding requires not just the answer but the provenance of the answer. Every claim needs a citation.

The Architecture Decisions That Held Up

Three decisions that aged well:

1. PRL as canonical representation

Every domain concept (competency, lesson, assessment, evidence) is a PRL primitive. The compiler validates structure before execution. This means: you can't inject malformed learning logic. The compiler catches it.

RAG equivalent: Schema validation on chunks before embedding. If a chunk doesn't match the expected structure, reject it before it enters the vector store.

2. Append-only evidence

Evidence is never deleted. Even failed assessments remain in the store. This gives you a complete audit trail — and it means the competency decision is reproducible.

RAG equivalent: Versioned document ingestion. When a document changes, the old version stays in the store (or is explicitly replaced). You can trace which version of a document generated an answer.

3. Competency gates

You can't bypass progression. The engine enforces it. This is fail-closed: if verification doesn't fire, progression doesn't happen.

RAG equivalent: Confidence thresholds. If retrieval confidence falls below your calibrated threshold, don't generate — say "I don't know" instead of guessing. Fail-closed, not fail-open.

The Numbers

The learning engine is not a deployed production system. It's a working reference implementation. The numbers below are from the test suite and development runs, not production traffic.

Metric Value Notes
Test suite 107 tests All passing
PRL primitives 6 types competency, lesson, assessment, evidence, verification, remediation
Competency dimensions 4 Cognition, Skills, Thinking, Values
Lesson stages 10 per lesson Fixed in PRL, not hardcoded
Evidence records Append-only Immutable once written
Chunking strategy Primitive-boundary Not token-boundary

What I didn't measure: Latency, cost per query, retrieval accuracy. These are future work when the RAG layer is added.

What I'd Do Differently

Three things, each mapping to a lesson from the cluster:

1. Build the evaluation framework before the learning logic

The test suite validates PRL compilation and engine execution. But there's no evaluation of learning outcomes. Does the competency model actually produce competent learners? I don't know.

RAG equivalent: Piece #7's evaluation cost center. Build the eval framework first, before tuning anything. You can't improve what you don't measure.

2. Start with hybrid retrieval for PRL keywords

When the RAG layer is added, exact-match retrieval on PRL keywords (competency_id, evidence_type) will be as important as semantic search. I'd start with hybrid, not add it later.

RAG equivalent: Piece #6's retrieval decision. Hybrid is the production default, not an enhancement.

3. Set chunking strategy based on document structure

The first version chunked by token count and broke PRL structure. The second version chunked by primitive boundary. The third version (not yet built) will embed each chunk with metadata that includes the primitive type, competency ID, and dimension.

RAG equivalent: Piece #6's chunking decision. There is no default chunking strategy. There is only the strategy that fits your document structure.

What This Means for Your Project

If you're building a RAG system, the learning engine is the application layer that sits on top. It's what decides what to do with the retrieved information — how to verify it, how to present it, how to gate progression based on it.

The RAG pipeline is the retrieval layer beneath it. It's what finds the relevant information in the first place.

You need both. The learning engine without RAG can only answer questions covered by the lesson flow. The RAG pipeline without an application layer can only retrieve — it can't decide what to do with what it found.
